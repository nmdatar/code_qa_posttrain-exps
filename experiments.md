# Experiments, in recommended order

Research checked September 28, 2026. Start with **Qwen3.5-4B**, then repeat the strongest results on **Qwen3.5-9B**, as specified in the [project description](PROJECT_DESCRIPTION.md). Both appear in the [Tinker catalog](https://tinker-docs.thinkingmachines.ai/tinker/models/). Record exact checkpoint IDs: these are starting models; a pretrained `-Base` checkpoint is a separate initialization experiment.

Use our generated training tasks for fresh, on-policy RL rollouts; use verified teacher trajectories for optional SFT. Freeze repository-family train/dev/test splits, calibrate the evaluator, and reserve public benchmarks for final evaluation. Compare **accepted-answer rate first**, then tokens, tool calls, latency, and all-attempt cost per accepted answer. Keep budgets and initialization fixed within comparisons; report both learning per sampled token and total training cost, including grading and auxiliary models. Repeat finalists across three seeds with repository-clustered uncertainty. The studies below are proposals, not established wins on this task.

1. **Establish the starting policy: untouched model vs SFT.** Evaluate the starting 4B checkpoint, then SFT it on verified investigations from our dataset using the baseline harness. Measure tool-call validity, grounded answer quality, and efficiency. Choose a common initialization for experiments 2–4; later compare the winning RL recipe with and without SFT. Mask tool observations and prompts in all training losses. This separates learning the interface from learning better investigation strategies.

2. **Plain REINFORCE: does the dataset produce useful learning?** Use the existing terminal reward and fresh complete episodes, with vanilla `A = R`, one on-policy update per batch, no critic, and no clipping. Then separately test a running reward baseline estimated from earlier batches to reduce variance. Track development acceptance and reward variance, not just training reward. REINFORCE-style RLHF research motivates this simple control, but its results do not establish vanilla REINFORCE as best for repository Q&A. [Research](https://arxiv.org/abs/2402.14740).

3. **GRPO: does comparing attempts at the same question help?** Compare experiment 2 against standardized within-question advantages, initially four rollouts per task; test eight only if useful. Keep the total rollout-token budget comparable and log zero-variance groups. First run the project's proposed single-pass, unclipped variant; then ablate PPO-style clipping, followed separately by reference KL. Name each recipe explicitly so normalization, clipping, and regularization are not confused. [GRPO paper](https://arxiv.org/abs/2402.03300), [project recipe](requirements/TRAINING_ARCHITECTURE.md).

4. **PPO and a learned reward model: test the two ideas separately.** First compare actor–critic PPO against GRPO using the same existing verifier reward. Then run a small 2×2: **GRPO/PPO × verifier/learned reward**. Train the reward model on evidence-reviewed pairs of attempts at the same training question; check ranking accuracy on development repositories before RL. Preserve deterministic failure gates and evaluate every arm with the independent correctness evaluator. The PPO critic estimates future return; the reward model scores outcomes. Measure whether either pays for its extra compute and whether reward rises while real quality falls. Tinker's clipped loss accepts supplied advantages; full critic training needs a capability check or another backend. [PPO](https://arxiv.org/abs/1707.06347), [Tinker losses](https://tinker-docs.thinkingmachines.ai/tinker/losses/), [reward overoptimization](https://arxiv.org/abs/2210.10760).

5. **Efficiency reward: can the agent finish sooner without cutting corners?** With the winning optimizer, compare quality-only reward against the existing acceptance-gated efficiency bonus; then vary token versus tool/runtime cost within that bonus. Preserve the failed/partial/accepted ordering and independent evaluation gates. Inspect premature stopping, missing essential claims, and unnecessary investigation. Select a quality–cost tradeoff, not the highest scalar reward. [Current reward contract](requirements/AGENT_HARNESS.md).

6. **Code tools and execution environment: which capabilities earn their cost?** Freeze policy weights. Start with list/search/read; add symbol definitions/references, then bounded tests/probes, one capability at a time. Separately compare generic shell commands with structured tools offering equivalent capabilities. Report results by lookup, cross-file, and runtime question type; keep execution-required questions identifiable. With capabilities fixed, compare cold versus prebuilt/warm isolated sandboxes and measure provisioning separately from answer latency. [SWE-agent](https://arxiv.org/abs/2405.15793) motivates interface ablations, though its benchmark concerns code repair.

7. **Context tools and representation: what evidence should enter the window?** Add a `get_context(query, budget)` tool. Compare lexical source snippets, hybrid lexical/embedding retrieval, and a compact symbol/dependency repo map at equal returned-token budgets. Separately compare automatic context injection against on-demand retrieval of the same representation. Then test raw history versus compact evidence notes plus retrievable old tool outputs, tracking citation loss and repeated reads. [Aider repo maps](https://aider.chat/docs/repomap.html), [contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval).

8. **Stronger-model repo annotations: can preprocessing make 4B cheaper?** Compare the winning raw-code index with question-independent, stronger-model annotations: first file/module summaries, then chunk-level explanations of dependencies and behavior. Generate only from the pinned repository, with no questions, answers, or private rubrics; keep source links and verify final claims against code. Test identical retrieval with/without annotations, report indexing cost plus amortized cost at 1/10/100 questions per repo, and invalidate annotations when source changes. This tests transfer of contextual retrieval to our task rather than assuming summaries help. [Research basis](https://www.anthropic.com/engineering/contextual-retrieval).

9. **Combine winners, retrain, and scale.** Evaluate a 2×2 of starting/RL-trained policy × baseline/improved harness to expose interactions. Then retrain from the same initialization with the improved harness, since tool use learned under the old harness may not transfer. Repeat the baseline and winning training/harness combination on 9B. Choose the final system on development quality–cost results, then evaluate once on the untouched test set and reserved benchmark.

Run harness ablations with frozen weights before spending on retraining. REINFORCE, actor–critic PPO, and learned rewards extend the current SFT/GRPO implementation scope; this plan does not imply those plugins already exist.
